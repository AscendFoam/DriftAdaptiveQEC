DriftAdaptiveQEC 查重与相关工作深度调研报告
Executive summary
基于近一年内的论文、预印本、开源仓库与技术报告，我的结论是：我没有检索到与“CNN 从 GKP syndrome histogram 估计漂移，并周期性更新一个 FPGA 友好的线性快回路解码器参数”几乎同构的已发表工作。目前最接近的邻域，不是 GKP histogram 本身，而是四条线索的交叉：GKP / bosonic 软信息解码，硬件条件化或校准条件化神经解码，实时/FPGA QEC 解码，和自适应/漂移感知的控制或 prior 更新。这些线索已经非常接近你项目的“叙事外壳”，所以如果论文主张写得过宽，撞车风险会从算法层面的低-中，迅速上升到系统叙事层面的中-高。[1]
更具体地说，已有工作已经覆盖了以下邻域：
一是 GKP / surface-GKP / multimode GKP 的强 classical decoder 与 soft-information 路线，包括 surface-GKP 的动态 edge weighting、closest-lattice / approximate-MLD、以及 noisy-auxiliary correlation-aware decoding；二是 “慢变量条件化 + 快速推理”的系统思想，如 calibration-conditioned FiLM decoder 把慢变化校准数据编码后条件化到低时延 CNN；三是 低延迟、FPGA、real-time feedback 的工程路线，最近甚至已经出现了在超导平台上做闭环实时 QEC 的 FPGA + NN 解码演示；四是 利用 QEC 数据在线对抗 drift 的自适应控制，包括 decoder prior 优化与 reinforcement-learning control。你的项目如果继续推进，最有潜力的差异化主张不是“神经网络做 GKP 解码”，而是：在连续变量 GKP 漂移噪声场景下，以 teacher-anchored residual / calibration 方式，仅更新一个可固定点部署、可原子提交、可 HIL 验证的线性 fast path 控制参数。[2]
因此，当前最危险的叙事不是“没有工作做过这个”，而是把系统创新写成通用算法首创。你不能再安全地主张“first neural decoder for GKP”“first adaptive QEC under drift”“first hardware-aware neural QEC decoder”，因为这些大框架都已有邻近先例；你可以更稳地主张的是：first or early demonstration of a histogram-conditioned, teacher-anchored drift adaptation layer for GKP decoding under deployment constraints，前提是 P4 formal benchmark、机制诊断、以及 deployment-boundary 证据做扎实。[3]

Differentiation analysis and risks to the current narrative
最关键的结论是：你的“算法内核”尚未被直接撞车，但“系统故事”已经有多个近邻。 如果你把稿子写成“我们提出了一个 adaptive neural decoder for GKP”，那么会同时撞上 GKP neural decoding、adaptive / drift-aware QEC、hardware-conditioned neural decoding、以及实时 FPGA neural decoder 这几条线；如果你把稿子写成“我们提出 teacher-anchored residual calibration for a linear GKP fast path under deployment constraints”，那就会明显更安全。[19]
在“CNN 从 histogram 估计漂移并更新 GKP 解码参数”这个最具体的问题上，我当前能给出的判断是：没有找到明确同题工作。最接近的工作是 FiLM decoder 用校准数据条件化轻量 CNN、decoder prior 优化用硬件局部统计更新 prior、以及 RL control / decoder steering 用 QEC 数据追踪 drift；但它们都没有走到“GKP syndrome histogram → CNN → runtime parameter update”这个具体映射。换言之，你当前的创新空间确实存在，但必须把它写成specific mechanism + deployment contract，而不能只写成“neural adaptation”。[20]
在“teacher + neural residual”这一点上，文献给出的信号是复杂的。一方面，NMWPM、neural belief-matching、AI pre-decoder 这类工作都说明了保留 classical structure，只让神经部分学动态权重、hint 或 residual 是一条非常自然且越来越主流的路线；这对你的 residual-b 主线是正向支持。另一方面，一篇 2025 年的独立研究发现，从 MWPM 做直接 knowledge distillation 并未提升最终精度，反而显著增加训练时间。这意味着：teacher-guided 是合理的，但 teacher imitation 未必合理；更安全的设计是把 teacher 当成稳定底座与目标分解器，让 CNN 学 drift-induced residual / calibration，而不是学习 teacher logits 本身。[14]
你当前技术路线的一个理论弱点，是 histogram window 可能会丢失时间顺序与相位空间细粒度相关性。如果 drift 的本质是慢变化的均值偏移、方差膨胀、或 q/p 轴向各向异性，那 32×32 histogram 很可能足够；但如果 drift 伴随 episodic mode-switching、重尾异常、回路迟滞、或与上一个 correction action 耦合，单纯 histogram 可能不如低阶矩 + 分位数 + 最近窗口差分 + confidence signal 的组合稳定。近期的软信息、confidence、adaptive window 等工作都在强调：低维统计不是问题，问题在于统计是否保留了和失败概率最相关的量。因此，histogram 不是不能用，而是必须在机制诊断里证明“它到底保留了什么”。[21]
另一个工程弱点，是 只更新 bias b 可能会被审稿人视为 engineer’s trick。这个风险并不意味着路线错误；相反，它很可能是最稳的第一步。问题在于，如果论文没有证明“drift 主要体现为 syndrome-to-correction 映射中的平移失配，而非增益矩阵 K 的结构变化”，那么 residual-b 就会显得像对某个特定数据集做 patch。解决方法不是一上来让网络更新全部参数，而是做一组层次化 ablation：teacher-only、residual-b、residual-K、residual-(K,b)、CNN-only、和 statcalib-only。只要能证明 residual-b 在大多数 drift 模式下已经抓住主导误差源，并且在 latency / fixed-point / stability 上最优，它就不是 trick，而是deployment-aware inductive bias。[22]
Benchmark, baselines, and hardware relevance
你的 T23 P4 formal benchmark protocol，我建议首先锁死四类 baseline，而不是先扩展模型花样。第一类是 强 classical GKP baselines：closest-integer / nearest-plane 一类的轻量 teacher、、以及如果你的实验设置可兼容，。第二类是 soft-information / correlation-aware baselines：surface-GKP 的 analog-weighted matching、以及 所体现的 correlation-aware 思路。第三类是 calibration baselines：teacher-fixed、oracle-teacher、以及参考 的 statcalib / prior-update 路线。第四类才是 learned baselines：CNN-only、teacher+residual-b、teacher+residual-(K,b)、必要时再加一个 FiLM-style conditioning variant。[23]
benchmark 情景上，不要只做“静态 matched / mismatched + 一个 drift”；至少要覆盖六类场景：静态匹配、静态失配、piecewise-constant drift、random-walk drift、sinusoidal drift、突发漂移 / reset drift。每类 drift 再区分 q-only、p-only、q/p 非等方、以及 measurement-offset / ancilla-quality drift。如果资源允许，再加一类训练集未见的漂移法则作为 generalization holdout。原因很简单：现有 adaptive / calibration / confidence literature 已经把“能不能适应慢变化”这个问题从单场景推向了robustness across nonstationarity；你的 formal benchmark 也必须跟上。[24]
统计协议上，我建议把训练随机性和评测随机性分开写进 protocol。对每个 learned 方法，至少报告 5 个 training seeds；对每个 noise/drift 场景，用公共随机数生成相同 syndrome 流，对所有方法复用；每个点至少做 20 条 unseen evaluation traces，或者做到 95% 置信区间相对半宽低于预设阈值。与此同时，formal benchmark 的指标不能只有 LER；还应同时报告 correction MSE / logical-shift surrogate、更新滞后、commit 失败率、rollback 次数、以及 p50/p95/p99 latency。这是因为你的论文真正要说服人的，不只是“更准”，而是“在部署约束下更准且更稳”。[25]
关于 hardware / deployment / FPGA relevance，现有文献已经把门槛拉得很高。真正的硬件级 claim，今天至少意味着：明确的 latency budget、真实推理 runtime、接口 serialization 成本、fixed-point / quantization 效果、以及 commit/fallback 语义；而不是“某模型参数量不大，所以理论上可部署”。特别是最近的 FPGA real-time QEC 工作已经给出了明确的闭环 latency 量级，因此你的系统写法应该更保守：在目前阶段，最准确的表述是 bounded software HIL with mock/artifact/inproc evidence 与 deployment-boundary feasibility study，而不是 real-board HIL。等到 true .tflite runtime 与真板 smoke gate 完成后，再把叙事抬到“embedded / FPGA-like runtime path validated”。[26]
如果最终没有 real-board result，这个工作依然能投稿，但更适合“decoder methodology + systems constraints + reproducible benchmark”型 venue，而不是强实验硬件导向 venue。更现实的定位会偏向 QCE / IEEE TQE / QST 的方法或系统方向，或者更偏算法与建模的 PRA / Quantum / PRR，前提是 formal benchmark 和机制证据扎实。若只有 development smoke、没有 P4 formal benchmark，这些 venue 都还偏早；若有 formal benchmark、clear deployment contract、fixed-point / software-HIL 证据，即使没有真板，也已经形成可投稿包。若再加上 real-board smoke 与 true .tflite inference，投稿上限会明显上升，因为这能把“可部署性”从叙事补充变成实证补充。[27]
Recommended next experiments and revised roadmap
我建议你的后续任务优先级按“先 benchmark，后机制，后 runtime，最后真板”来排，而不是直接冲 paper packaging。第一优先级仍然应是 锁死 P4 formal benchmark protocol。这一步要做的不是把全部模型都跑完，而是先冻结：baseline 列表、noise/drift family、训练/验证/测试拆分、统计停止准则、latency 记录方式、quantized 与 float 的对照方式、以及 software HIL 的接口契约。只要这一层没有冻结，后面的机理分析和工程恢复都会不断返工。[28]
第二优先级是 机制诊断，但不要泛化成“解释网络为什么有效”，而要优先解释三个非常具体的现象。第一，histogram 中哪些统计量最能预测 drift-induced failure：均值偏移、轴向方差、偏度、边缘峰值、还是时间差分。第二，为什么 residual-b 足够，或在哪些 drift 模式下不够。第三，慢路 update 频率 / commit 频率 与性能和稳定性的 trade-off。如果这些现象解释清楚，论文贡献会从“engineering trick”升级为“deployment-aware control abstraction”。[29]
第三优先级是 paper-inspired statcalib branch。我的建议是：值得继续，但必须控制范围。它不一定要变成主线方法，却几乎肯定要成为 formal baseline，原因有二：其一，decoder prior / calibration optimization 在近年的 QEC literature 里已经被证明是实打实有效的；其二，它天然比 CNN residual 更容易做 safety fallback。如果资源紧，最合理的做法不是大投入做复杂 statcalib，而是尽快做出一个简洁、可复验、可原子提交的 statcalib baseline，哪怕只更新偏置或少数 gain 参数，也足以大幅增强论文说服力。[30]
第四优先级我会放在 恢复 true .tflite runtime，并且优先级应当高于 real-board smoke。原因不是 .tflite 本身更“学术”，而是因为它直接决定你能否把 slow loop 的部署边界写成真实运行边界，而不是 stub manifest。只要 true .tflite runtime 没打通，slow loop 的部署叙事就始终是半截的；相反，真板 smoke 即使做出来，如果整个 slow path 还是 stub，审稿人仍会认为系统闭环没有真正打通。因此，在资源有限时，我会先拿到 formal benchmark + true .tflite + quantized software HIL 的三件套，再考虑真板。[31]
第五优先级才是 real-board smoke gate。它对论文价值不小，但不是必须项，也绝不能替代 formal benchmark。它真正提供的是可信度乘数：证明 parameter bank / atomic commit / fixed-point / interface semantics 没有在真实 runtime 中崩掉。若没有它，工作仍可能投稿；若有它，尤其是能给出 deterministic timing、commit 成功率、以及与 software HIL 的误差对照，那么 systems 叙事会明显更强。可如果 formal benchmark 本身不完整，真板 smoke 的价值会大幅缩水。[32]
如果资源有限，我认为最小可投稿证据集应当是下面五件事，而不是更多。
一，P4 formal benchmark，且 baseline 足够强。
二，teacher-only / CNN-only / residual-b / statcalib 的关键 ablation。
三，至少一组未见 drift family 的泛化结果。
四，量化后的 software HIL，含 latency、commit、rollback、版本化 bank。
五，机制诊断至少回答“为什么 residual-b 有效”这一个核心问题。
满足这五件事，即使没有 real-board，也已经是一个可靠的“方法 + systems constraints”包；若再补 true .tflite runtime 和 board smoke，投稿空间会进一步扩大。[33]
从叙事上，我建议把你的 revised roadmap 改写成下面这个顺序。首先，以你当前已确认的边界为准，把现阶段严格表述为 controlled development with reproducible bounded software-HIL path，明确不是 real-board、不是 formal benchmark、不是已恢复真实 .tflite。其次，完成 P4 protocol 冻结并跑出第一版 formal benchmark。然后，围绕 residual-b 与 histogram representation 做机制诊断，并并行补一个简洁 statcalib baseline。再之后，恢复 true .tflite runtime，使 slow loop 的 deployment claim 可实证化。最后，如果资源允许，再把真板 smoke 作为 credibility booster 接入。这样写，既不会夸大当前状态，也能最大程度利用文献中尚未被占满的空白区。[34]
最后给出一个非常简短的底线判断：直接撞车风险目前不是“高”，但如果论文主张写成宽泛的 adaptive neural GKP decoder，风险会迅速升高；如果把主张收敛到 teacher-anchored residual calibration、histogram-conditioned slow loop、fixed-point linear fast path、atomic commit、software-HIL-to-runtime boundary，那么这个项目依然有清晰而且可发表的差异化空间。 目前最值得守住的不是“模型更复杂”，而是“主张更窄、更准、更可证”。[35]
