# 投稿稿统计不确定性与复现边界说明

本文档服务 `docs/paper_notes/CNN_FPGA_GKP_submission_draft.tex`。它把当前投稿稿中分散的统计、不确定性、source-data 和复现边界集中成一张审稿人可检查的 guardrail。本文档不运行新实验，不改变 `T24`、FR6/FR7、FR8/statcalib、`.tflite`、real-board 或 `T90` 的证据等级。

## 一句话结论

当前主结果可信为一个 locked mock-backed software-HIL frozen-set ranking：四个预声明 drift scenario、五个 mode、paired seed/repeat 设置、`repeats=2`。它还不可信为 statistical significance、broad robustness、expanded benchmark、cross-host reproducibility、deployment closure 或 real-board validation。

## 3. 稿件推荐写法

可以写：

- `The main result is a frozen-protocol software-HIL ranking with descriptive uncertainty only.`
- `Error bars denote descriptive standard deviations across the two available repeats.`
- `The current evidence supports a bounded systems-method claim, not a distribution-level superiority claim.`
- `The paired-bootstrap envelope is a descriptive resampling summary over n=2 paired deltas, not an inferential interval.`
- `Reproducibility is limited to recorded repository artifacts and current-host gates unless a future reproduction package is added.`

不要写：

- `statistically significant`
- `confidence intervals show`
- `p < ...`
- `robust across unseen drift families`
- `fully reproducible`
- `cross-host portable`
- `hardware validated`
- `deployment ready`

## 4. 投稿前应补的最小强统计材料

1. 预声明 inferential paired uncertainty 方案：同一 seed / scenario / mode 下比较 hybrid 与 UKF、EKF、RLS、constant baseline 的 paired differences；当前只有 descriptive UKF-vs-Hybrid envelope。
2. 更高 repeats 或正式 bootstrap/paired bootstrap：当前已补 `submission_draft_benchmark_expansion_protocol.csv/json` 作为规划材料，建议 Phase A 每个 scenario 至少 12 个、目标 16 个 paired repeats；`submission_draft_runner_smoke_pair.csv/json` 只证明单场景 smoke pair 可执行，正式执行前仍不得写成已完成 CI / p-value。
3. Effect size：至少报告 hybrid 相对 UKF 的 absolute LER difference 和 relative reduction，并给出 uncertainty。
4. Holdout drift family：至少一个未参与当前 frozen set 的 drift scenario，用于区分 frozen-set ranking 和泛化。
5. 扩展 table-to-artifact audit helper：当前第一版 helper 已自动核对主结果、Fig. 2-4 source CSV、T24 `comparison.csv`、T24 `summary.json` 和 manifest；投稿前仍需覆盖全文表格、per-row artifact hash、runner version 和 environment manifest。
6. Source-data manifest：每个 result row 应包含 scenario、mode、seed/repeat policy、metric definition、config hash、commit、artifact path/hash、runner version 和 environment note。

## 5. 审稿人可信度判断

审稿人可以信当前稿件的三件事：

1. 作者没有把 mock-backed software-HIL 写成 real-board 或 deployment；
2. 主结果有锁定协议、run root、review 和 source CSV 回链；
3. 稿件主动承认 `n=2` descriptive SD、无 CI、无 holdout、无 hardware result。

审稿人仍会质疑三件事：

1. `repeats=2` 太少，无法支撑强统计结论；
2. provenance 已有第一版机械一致性检查，但覆盖范围仍窄，还缺全文表格、per-row hash 和 runner version；
3. 论文若标题/摘要保留 hardware-facing 语言，硬件占位符会显得过强，除非后续补真实板级材料。
