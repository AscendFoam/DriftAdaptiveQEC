# Paper Claim/Evidence Ledger

## 1. Scope And Non-Claims

This document is a paper-assembly boundary ledger, not a paper draft and not a new experiment report.

It only records what the repository can already support with concrete paths under the current `Phase 2: Controlled Development` boundary.

It does not:

- upgrade any mock-backed, stub, readiness, or smoke evidence into a stronger completion claim
- treat `.tflite` entrypoints or stub manifests as true runtime validation
- treat `board_backend.py` scaffolding or readiness plans as real-board validation
- treat one clean-environment CPU smoke as full training reproducibility or portability
- rewrite frozen-set formal software revalidation into paper-grade expanded benchmark evidence

Status labels used below:

- `supported`: the bounded claim is directly backed by concrete existing evidence
- `partial`: there is real evidence, but the claim needs a narrower wording boundary
- `blocked`: current repo evidence is not strong enough to write the claim as completed

## 6. Wording Guardrails For Future Paper Drafting

1. Replace `hardware validated` with `mock-backed software HIL revalidation` unless the cited evidence path is a real-board run artifact.
2. Replace `TFLite deployed` with `TFLite entrypoint/stub path exists` unless the cited evidence path shows a true runtime environment and a true `.tflite` run.
3. Replace `training reproducible` with `one clean-environment CPU-only smoke completed` unless cross-run, cross-platform, or broader portability evidence is added.
4. Replace `mechanism proven` with `single-seed trace-supported diagnosis` unless multi-seed or mitigation evidence closes `R10`. After T55, also replace `high committed-b is harmful` or `committed-b instability should be reduced` with `committed-b instability is broadly present and mostly correlates with Gv5 advantage`; do not assume instability = defect.
5. Replace `benchmark complete` with `frozen-set formal software revalidation complete` unless the paper intentionally introduces a new expanded benchmark task and evidence pack.
6. When a claim depends on `hybrid_residual_b`, state whether the scope is the frozen T24 set or the teacher-representation diagnosis lane; do not merge those lanes implicitly.
7. Keep `statcalib` wording in three separate buckets: `feasibility gate`, `interface contract`, and `integrated comparator evidence`; never collapse them into one sentence.
8. Replace `feature ablation proves the teacher design` with `T57 provides a bounded frozen-set ablation table whose interpretation remains non-causal`; the no-teacher-params variant unexpectedly performs best, so strong attribution wording is unsafe.
