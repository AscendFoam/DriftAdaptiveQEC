# 投稿稿物理噪声与逻辑错误边界审计

日期：2026-07-02

对象：`docs/paper_notes/CNN_FPGA_GKP_submission_draft.tex`

性质：投稿稿写作材料与边界审计；不新增实验，不重跑 benchmark，不升级任何 HIL、`.tflite`、real-board 或 deployment 证据等级。

## 一句话结论

当前稿件可以把方法表述为“在近似 GKP 综合征模型下，以软件-HIL 协议验证的 drift-adaptive affine calibration”。它还不能写成完整物理噪声模型、真实硬件验证、普适 GKP decoder 优越性，或严格物理逻辑信道错误率结论。

## 已能支撑的物理与指标锚点

| 主题 | 当前代码/材料锚点 | 可写入稿件的边界 | 不可外推 |
| --- | --- | --- | --- |
| GKP 晶格常数 | `physics/constants.py` 统一 `LATTICE_CONST = sqrt(2*pi)` | 理论节可使用 `lambda = sqrt(2*pi)`，并说明代码侧共享同一常数 | 不能因此声称已完成全物理模型验证 |

| 逻辑错误判定 | `physics/logical_tracking.py` 以 q/p 累积位移越过 `±LATTICE_CONST/2` 计 X/Z 错误，并 wrap 回基本区间 | 可说明软件协议中的 LER 来自残差累积边界判定 | 不能写成真实逻辑信道 tomography、实验 logical failure rate 或 outer-code threshold 证据 |
| fast-loop 协议指标 | `cnn_fpga/runtime/fast_loop_emulator.py` 以 `LogicalErrorTracker` 记录 `final_logical_error_rate`，并输出直方图/校正饱和诊断 | 稿件可称为 fixed software-HIL protocol 下的 `final_ler` proxy | 不能写成物理硬件 LER、confidence interval、显著性检验或 holdout generalization |

| affine map | `cnn_fpga/decoder/param_mapper.py` 从 `NoisePrediction(sigma, mu_q, mu_p, theta_deg)` 映射到 `K,b`，使用协方差型 gain 与偏置规则 | 可支撑“slow loop updates committed affine parameters”的方法说法 | 不能写成最优 GKP posterior decoder 或已证明的 universal calibration law |

## 审稿人会追问的问题

1. `final_ler` 是否是真实逻辑错误率？

   当前答案应保守：它是 software-HIL fast-loop emulator 中由残差累积边界判定产生的协议指标。虽然该指标使用 GKP 半晶格边界和 wrap 逻辑，但当前主结果不是真实硬件上的 logical error rate，也不是独立物理实验测得的 logical channel。

2. `lambda = sqrt(2*pi)` 与代码实现是否一致？

   一致性有明确代码锚点：`physics/constants.py`、`syndrome_measurement.py`、`logical_tracking.py`、`fast_loop_emulator.py` 均使用共享的 `LATTICE_CONST` 或从该常数派生的半晶格边界。已补 `audit_submission_draft_symbol_boundary.py` 作为投稿材料级轻量审计 helper，把 TeX 符号、wrap 区间、logical threshold、fast-loop metric 和 Fig. 2 `n=2` descriptive-SD 边界机械对齐；它仍不是完整物理模型验证。

3. 有限能量 GKP 模型是否充分？

   不充分。代码有 `delta`、测量效率、shot noise 和 ancilla error 的近似实现，但稿件不能把它写成完整 finite-energy GKP physical model。推荐正文用 “approximate GKP syndrome model” 和 “local affine approximation”，并把 branch ambiguity、multimodal wrapped posterior、finite-energy envelope 作为边界。

4. 四个 drift scenario 是否代表真实设备漂移？

   不代表。它们是 hand-designed synthetic effective-state probes，适合测试 calibration contract 的不同压力面。投稿前如果想提升可信度，至少需要一个 unseen holdout drift family、一个由真实或更物理的 noise generator 产生的 source-data manifest，以及场景参数的机器可读 field-to-symbol ledger。

5. 当前实验是否可信？

   可信范围有限：作为 frozen software-HIL ranking 和写作材料，它有明确 source CSV、figure source data、provenance、descriptive SD、artifact boundary 和 source-data audit。作为高质量期刊主结论，它仍弱：`repeats=2`、无 CI/显著性、无 holdout、缺 oracle/known-noise/wrapped-Gaussian baseline、缺硬件测量、缺完整物理噪声审计。

## 建议正文措辞

可用：

- “approximate GKP syndrome model”
- “local affine approximation near a lattice branch”
- “effective synthetic drift state”
- “fixed software-HIL protocol”
- “final logical-error proxy”
- “descriptive standard deviation across two repeats”
- “hardware-facing placeholders”

避免：

- “complete physical noise model”
- “true logical error rate measured on hardware”
- “hardware validation”
- “deployment closure”
- “statistically significant improvement”
- “state-of-the-art GKP decoder”
- “generalizes across realistic device drift”

## 对当前投稿稿的直接修改建议

1. 在 `Problem Setting` 后补一个短的 `Physics-Model and Metric Boundary` 小节，明确五件事：wrap 常数、有限能量近似、effective drift、`final_ler` proxy、硬件空缺。
2. 在 `Theory-to-Configuration Bridge` 中保留 “Physics-level syndrome wrapping and logical-channel audit” 的缺口，但补充本审计的代码锚点，避免读者误解为完全没有实现依据。
3. 在 Results 中继续把主表写成 frozen-protocol ranking，不加 “significant” 或 “robust”。
4. 在 Discussion 中把缺口从泛泛 limitation 改成 reviewer-facing action list：stronger baseline、holdout、CI、hardware source data、physics audit helper。
5. 在 source-data/figure material 中继续标注 Fig. 2 的误差条是 descriptive SD，不是 confidence interval。

## 推荐的投稿前最低闸门

如果目标是“可认真外投但仍以 software-HIL 方法稿为主”，最低需要：

1. 将已补的 physics/code-symbol audit helper 扩展为可持续维护的单元测试或 CI preflight；
2. 增加一个 oracle/known-noise affine 或 wrapped-Gaussian 小基线；
3. 增加一个 holdout drift 或 random-walk/burst stress scenario；
4. 把主结果 repeats 从 2 提高到可报告 paired CI 的水平；
5. 保留 hardware placeholder，除非真实板任务已经产生完整 source data。

如果目标是“硬件/FPGA 实证论文”，当前材料还不够，必须先补真实 board execution、bitstream/RTL provenance、DMA trace、latency/resource report、host/device agreement 和 failure logs。
